# 自动化测试循环规程

> 供 `/loop` 反复调用。**每轮 = 主块（阶段一/二）+ 三态例行（§3），做完写回文件就退出。**
> 状态全部存在各 md 的「计划变化」列里，不依赖上下文记忆。

调用方式：

```
/loop 20m 按 imboyapp/test/auto_test/LOOP_PROMPT.md 执行一轮
```

---

## 0. 每轮开场：先定位自己在哪个阶段

在 `imboyapp/` 目录下执行：

```bash
grep -rh '^| ' test/auto_test/*/*.md | grep -v '^| 计划变化' | awk -F'|' '{gsub(/ /,"",$2);print $2}' | sort | uniq -c
```

按结果决定本轮主块做什么：

| 条件 | 阶段 | 动作 |
|---|---|---|
| 还有 `待首测` | **阶段一：测试** | 走 §1 |
| 无 `待首测`，还有 `待修复` | **阶段二：修复** | 走 §2 |
| 两者都为 0 | 主块无可用 | 主块跳过，直接做 §3 |

**每轮无论主块是什么，都必须完成 §3 三态例行（待复验/回归复测/阻塞各处理一条）。**
`待首测` 和 `待修复` 清零后，三态例行就是每轮的全部内容。

## 1. 阶段一：测试（只测不修，绝不改代码）

### 1.1 选取本轮目标

按 `test/auto_test/` 目录字典序，找**第一个仍含 `待首测` 行的 md 文件**，本轮只做这一个文件。

一次一个页面。不要贪多——上下文越长越容易误判。

### 1.2 环境前置校验（每轮都要做，不要假设）

```bash
adb devices                       # 华为 MRD_AL00 在线
adb shell dumpsys package imboy.chat | grep -E "versionName|lastUpdateTime"
```

确认：设备在线；APK 构建时间**不早于** `git log -1 --format=%ad`。
若 APK 比 HEAD 旧，说明装的不是当前代码，**先重新构建安装再测**，否则测的是旧版本。

账号：117@imboy.pub(uid50) / 生产 pro.imboy.pub。

### 1.3 逐个功能点验证

对该文件里每一条 `待首测` 行：

**操作前**：`adb logcat -c` 清空日志。

**操作**：用 mobile MCP 导航并执行该功能点描述的操作。

**判据，按优先级：**

1. **logcat 是主判据**
   ```bash
   adb logcat -d -s flutter | tail -40
   ```
   **写操作类（发送/点赞/保存/删除/上传/订阅）必须看到服务端成功日志才算通过。**
   UI 变了不算数——那可能是乐观更新，失败回滚后画面和「什么都没发生」一模一样。
   典型成功日志形如 `ChannelService: 添加消息反应成功`、`创建评论成功`。

2. **get_ui 判结构**：该有的按钮/入口在不在；是不是只剩一个返回键（空壳页的典型症状）。

3. **截图判视觉**：布局溢出、颜色规范、图片渲染、浮层遮挡、断词换行。
   - **toast / snackbar 必须在操作后 1 秒内截图**，晚了必把「有反馈」误判成「静默失败」
   - `get_ui` 返回空或节点数只有个位数时，**必须补截图**再下结论——
     Flutter 语义树自己会崩，空结果不等于白屏

### 1.4 必须跳过的情况（标注原因，不要硬试）

- 会打扰真实第三方：给真人好友发消息、外发通知、@提及
- 会写生产资金数据：充值、转账、发红包、提现
- 不可逆：注销账号、删除群、清空聊天记录、E2EE 密钥导入/恢复
- 缺外部条件：需第二台设备、需真实素材、需 20 人以上的群

遇到这类：该行改为 `计划变化=阻塞`，`计划时间` 写清楚**需要什么条件才能测**。

### 1.5 立即回写（每验完一个功能点就写，不要攒到最后）

**只覆盖现有行，绝不新增行。**

| 结果 | 计划变化 | 计划时间 | 测试状态 | 测试轮次 | bug 三列 | 备注 |
|---|---|---|---|---|---|---|
| 通过 | `无待办` | `-` | `已通过` | `批次N` | 不变 | 清空 |
| 发现问题 | `待修复` | 当天日期 | `有BUG待修` | `批次N` | 发现+1、待处理+1 | 现象一句话，30 字内 |
| 条件不具备 | `阻塞` | 解阻塞条件 | `未测` | `批次N` | 不变 | 缺什么 |

恒等式必须始终成立：**待处理 = 发现 − 解决**。

### 1.6 本轮收尾

该文件所有 `待首测` 处理完即停止。

**收尾前必须做两件事，缺一不可：**

```bash
# 1. 重生成 README 的汇总与模块索引（否则统计陈旧）
python3 test/auto_test/regen_readme.py

# 2. 校验 bug 三列恒等式（脚本会自己报错，也可单独跑）
grep -rh '^| ' test/auto_test/*/*.md | grep -v '^| 计划变化' \
  | awk -F'|' '{gsub(/ /,"",$8);gsub(/ /,"",$9);gsub(/ /,"",$10);
      if($8~/^[0-9]+$/ && $8-$9!=$10) c++} END{print "违反行数: " c+0}'
```

`regen_readme.py` 在恒等式不成立时会以非零码退出——**退出即说明有行写错了，
必须查出来改对，不要绕过**。

然后输出：

- 测了几个功能点，通过几个、发现几个 bug、跳过几个
- 每个新 bug 一句话（页面 + 现象 + logcat 关键证据）

**阶段一绝不改任何代码。** 发现的 bug 只记录，留到阶段二。

## 2. 阶段二：修复

前提：全部 `待首测` 已清零。

### 2.1 选取

按目录字典序找第一个含 `待修复` 行的 md 文件，本轮处理该文件里的全部 `待修复` 项。

### 2.2 定位根因（这一步最容易出错，慢一点）

- **改之前先 grep 所有调用点。** 同一根因常常影响多处——在共享函数上加一个守卫，
  比在每个调用点各加一遍的 diff 更小，也不会漏掉兄弟调用点
- **不要靠猜改代码。** 假设未被证据证实前，一律在输出里标明「这是假设」
- 历史教训：25 个批次里 5 次判定被自己推翻、2 次修复引入了更严重的回归

### 2.3 改完先跑单测

```bash
flutter test test/unit_test/<相关目录>
```

注意：`test/` 下不得出现需要设备的 `*_test.dart`，端到端测试在根目录 `integration_test/`。

### 2.4 真机复验

该文件全部改完后，一次性构建安装，再逐项复验：

```bash
flutter build apk --debug && adb install -r build/app/outputs/flutter-apk/app-debug.apk
```

复验回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复验通过 | `无待办` | `已通过` | 解决+1、待处理−1 | 清空 |
| 复验不过 | `待修复` | `有BUG待修` | 不变 | 写清楚**哪一步没过** |

### 2.5 收尾（与阶段一同样强制）

```bash
python3 test/auto_test/regen_readme.py
```

### 2.6 提交

```
fix(<模块>): <一句话>

<现象>
<根因>
<修法>
<验证：单测结果 + 真机复验结果>
```

注意：`lefthook` 的 `dart-fmt` 钩子失败会**静默吞掉 commit**，提交后必须
`git log --oneline -1` 确认真的提交上了。用 `-F 消息文件` 而非 `-m`。

**不要推送。** 推送是外向操作，等人工确认。

## 3. 每轮例行：三态各处理一条（待复验 / 回归复测 / 阻塞）

无论主块是阶段一还是阶段二，**每轮都要从这三个状态各挑一条处理**。
`待首测` 与 `待修复` 清零后，本节就是每轮的全部内容——靠它把 642 条回归复测
和 409 条阻塞逐步消化掉。

### 3.1 选取（各取全量列表的**最后一条**）

```bash
grep -rh '^| ' test/auto_test/*/*.md | grep -E '^\| (待复验|回归复测|阻塞)' | tail -1
```

- **为什么取最后一条而不是第一条**：阻塞有 400+ 条，每轮从头取会永远卡在同一条上；
  取最后一条，多轮跑下来自然从尾部向头部全覆盖
- 三个状态各跑一次上面的命令，各得一条；若某状态为 0 条则本轮跳过该状态

### 3.2 复验前置：APK 时间线判定（先做，不满足就不测）

```bash
adb shell dumpsys package imboy.chat | grep lastUpdateTime   # APK 构建时间
git log -1 --format=%ad -- <该行涉及的修复提交>              # 修复提交时间
```

- 该行备注里写「已修」的，找到对应修复提交；**修复提交晚于 APK 构建时间 =
  修复不在当前 APK 里，真机测不出结果**，不要硬测
- 此时：`计划变化` 改为 `阻塞`，`计划时间` 写 `待新APK`，测试状态不变，
  bug 三列不变——等新 APK 装好后下轮从阻塞里把它捞回来
- 修复已在 APK 内（或该行无修复、纯功能回归），才继续真机测

### 3.3 待复验：真机复验

按 §1.3 判据执行该功能点。回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复验通过 | `无待办` | `已通过` | 解决+1、待处理−1 | 清空 |
| 复验不过 | `待修复` | `有BUG待修` | 不变 | 写清楚哪一步没过、logcat 证据 |

### 3.4 回归复测：补单独验证历史功能点

挑出的行是「页面整体标过通过、但这个功能点当初没被单独验证」的历史点，
本轮补上单独验证（判据同 §1.3）。与 `待首测` 的区别：待首测=整页从没进过
测试轮；回归复测=同页其他点测过、该点被带过。回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复测通过 | `无待办` | `已通过` | 不变 | 清空，测试轮次改当前批次 |
| 发现回归 | `待修复` | `有BUG待修` | 发现+1、待处理+1 | 现象一句话 + logcat 证据 |

### 3.5 阻塞：只评估解阻塞条件，不硬试

阻塞是「缺条件测不了」，**不要真机硬试**（条件真缺时测了也是噪音）。按备注里的
`计划时间`（即解阻塞条件）逐类检查：

| 阻塞类型 | 检查什么 | 条件满足后 |
|---|---|---|
| `待发布生效` | 服务端是否已发布（如版本号/API 行为已变、迁移已执行） | 转 `待复验`，测试状态 `待重验` |
| `待新APK` | APK 构建时间是否已晚于修复提交（`dumpsys lastUpdateTime` vs `git log`） | 转 `待复验`，测试状态 `待重验` |
| `待产品决策` | 人工决策是否已定（查 git log / 对话，不要替用户拍板） | 已定=转 `待复验`；未定=维持 |
| `缺外部条件` | 条件是否已具备（第二台设备/素材/凭据） | 已具备=转 `待复验`；仍缺=维持 |
| 其余 | — | 维持 `阻塞`，本轮不改动 |

**维持不改动的行，只在本轮输出里说「检查过，条件仍缺」，不碰表格。**
每轮只处理一条，409 条按尾部推进逐步消化。

### 3.6 三态例行收尾（同样强制）

三态处理完、主块收尾后，统一执行：

```bash
python3 test/auto_test/regen_readme.py   # 恒等式不成立会非零退出，查错改对，不要绕过
```

并校验恒等式（§1.6 的 awk 命令）。

### 3.7 提交

三态例行改动的是测试计划文档（md），同样要提交，用 pathspec 精确提交本次
动过的文件（**不要无 pathspec 的 commit**，会打包并发会话 staged 文件）：

```
docs: 测试计划更新（批次N：<待复验1条结果>/<回归复测1条结果>/<阻塞1条评估>）
```

## 4. 每轮都要遵守的铁律

1. **只信 `git status --porcelain`**，不信自己「我改了什么」的记忆
2. **判定要有证据**。写「通过」必须有 logcat 或截图支撑，不能靠「看起来对」
3. **判断运行时状态要问运行时**，不要用静态读代码代替真机验证
4. **发现自己此前判断错了，直接更正并说明**，不要藏
5. **绝不新增表格行**，只覆盖。行数增长 = 文档失控
6. **本轮范围外的事不做**：不重构、不优化、不顺手改别的
