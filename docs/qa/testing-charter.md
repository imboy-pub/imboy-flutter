# imboyapp 客户端自动化测试架构(测试宪章)

> 定位:**这是 imboyapp(Flutter IM 客户端)的测试策略主干,回答"用什么样的自动化测试体系,能持续保证一个即时通讯软件的稳定、可用、并测出可用性 bug"。**
> 状态:蓝图稿,待 review。本文档只做架构与规划,不含已执行的代码改动。
> 生成日期:2026-07-18 | 视角:软件质量架构师

---

## 0. 核心命题

一个 IM 客户端的质量,不能用通用 App 的测试金字塔来保。因为 IM 的本质是**"两个端之间的可靠通信"**——它的生死线是"消息不丢、不重、不乱序、多端一致、断网能恢复",这些**单端跑再多单元测试也测不出来**。

因此本架构的两条主线:
1. **风险驱动**:测试投入对准 IM 的 8 大质量维度 + imboy 自己的历史事故地图(§1、§2),不追覆盖率数字。
2. **分层 + 双端**:6 层架构把 bug 压到最低的可靠层测(§3),并以**双端场景库**(§4)作为"软件是否可用"的客观验收中枢——这是 IM 测试区别于普通 App 的关键。

---

## 1. 定义"质量":IM 客户端的 8 大维度

| # | 质量维度 | 典型失败形态(用户可感知) | 严重度 |
|---|---|---|---|
| Q1 | **消息投递正确性** | 丢消息 / 重复 / 乱序 / 发出对方没收到 | 🔴 致命 |
| Q2 | **本地数据完整性** | 迁移损坏历史、重装丢记录、未读数算错 | 🔴 致命 |
| Q3 | **连接韧性** | 断网不重连、重连不补历史、心跳死 | 🟠 严重 |
| Q4 | **多端一致性** | A 已读 B 仍未读、多端收不齐 | 🟠 严重 |
| Q5 | **E2EE 正确性** | 解不开密文、换设备打不开旧消息、明文泄漏 | 🔴 致命 |
| Q6 | **可用性/交互** | 卡转圈、气泡渲染错、发送按钮无反应 | 🟡 高频 |
| Q7 | **性能** | 大历史滚动卡、会话列表刷新慢 | 🟡 中 |
| Q8 | **真机兼容** | iOS/Android 渲染差异、键盘遮挡 | 🟡 中 |

**架构第一原则:每一层测试的存在,都必须能回答"它守住 Q几"。守不住任何维度的测试是噪声。**

---

## 2. 风险地图:imboy 自己流血的地方(测试重心的依据)

不需要猜 bug 在哪——历史事故就是最精确的风险地图。每条都标注了它**应该被哪一层拦住**:

| 历史事故类 | 对应质量维度 | 应设防层 |
|---|---|---|
| 契约漂移(build_select / read_part / TSID 精度) | Q1 | L0 契约 + L3 集成 |
| WS 协议(bad magic 裸 protobuf / ws_url 配置错) | Q1 Q3 | L0 契约 + L3 |
| 离线同步(离线消息流 / 归档追平) | Q1 Q4 | L1 逻辑 + L4 双端 |
| 多端投递(T03 按设备 ACK) | Q4 | L4 双端 |
| 状态丢失(#33 autoDispose 只 read 不 listen) | Q6 | L2 组件 |
| 本地迁移(SQLite v17/v18 升降级) | Q2 | L1 迁移测试 |
| 消息状态机(ack / retry / dedup) | Q1 | L1 逻辑 |
| E2EE(密钥托管 / 换设备恢复) | Q5 | L1 加解密 + L4 双端 |
| 附件链路(presign 上传 / 渲染授权) | Q6 | L3 + L4 |

**结论:imboy 最痛的是 Q1(投递)和契约漂移。测试架构的重心必须压在 L0/L1/L3/L4 这条"通信正确性"链上,而非堆 UI 单测。**

## 3. 六层测试架构

原则:**在能给出可靠信号的最低层测**——把消息逻辑 bug 压到 L1(快、确定),不要拖到真机才发现。

### L0 · 契约层(每 PR · 秒级 · IM 的脊椎)
- **守**:Q1 — WS 帧格式、消息信封 schema、API payload 字段名+类型
- **做法**:契约定义为**前后端共享的单一事实源**(proto / JSON schema),客户端与 Erlang 后端都从它生成或校验。后端改字段 → 客户端契约测试立即红。
- **守的事故**:契约漂移、bad magic、ws_url
- **现状**:`ws_api_test.dart` 是唯一真契约测试(8/10),应扩展为体系

### L1 · 逻辑/状态机层(每 PR · host · 无网无设备 · 最高 ROI)
- **守**:Q1 Q2 Q5 — 消息状态机(sent→ack→delivered→read / retry / dedup / ordering)、离线队列、未读数计算、会话列表合并排序、SQLite 迁移(对真迁移文件跑)、E2EE 加解密往返
- **守的事故**:离线同步、迁移损坏、消息状态机、E2EE 加解密
- **现状**:`test/service` + `test/integration` 已在此层且质量不错(~85% 真行为)——**这是核心资产,保留强化**

### L2 · 组件行为层(每 PR · host · widget · 当前最薄)
- **守**:Q6 — ChatPage 在各消息类型下的渲染、事件驱动 UI 更新(EventBus→列表刷新)、输入/发送交互、未读角标
- **守的事故**:#33 autoDispose 丢数据、渲染错、按钮无反应
- **现状**:ChatPage(1808 行)几乎空白,最该补;现有 page 测试约 1/3 是"改坏也不红"的稻草人(§6 退役)

### L3 · 契约集成层(每 PR · CI 起真后端 docker · 防漂移实弹)
- **守**:Q1 Q3 — 真 HTTP/WS 打到容器化的真 imboy 后端:登录 / 收发 / 同步
- **守的事故**:契约漂移的动态活体验证(L0 静态,L3 动态)
- **现状**:`test/api` 管道是真的,但 CI 不起后端 → 全 skip 空绿(**必须修**)
- ✅ **已确认后端可容器化 → L3 定为 PR 硬门**

### L4 · 双端场景层(nightly + 发版前 · 真机 · IM 杀手锏 ★)
- **守**:Q1 Q4 Q5 Q6 — 两个真实账号,A 发 B 收,验证收齐/顺序/未读/已读、离线→上线补历史、换设备→历史恢复、真机渲染导航
- **守的事故**:多端投递、离线同步、E2EE 换机、可用性——单端永远测不出
- **现状**:已有 `integration_test/chat/support/dual_test_helper.dart` + `account_identity` 脚手架 → **方向正确,应做成验收中枢**(详见 §4)
- **落地路径**(2026-07-29 更新):integration_test 真机(现役) → Patrol Android(主 E2E,待接入);macOS 桌面作无设备兜底。~~方案 B Maestro~~ 已删除(Flutter Key 不接无障碍层)

### L5 · 非功能层(周期性 · 稳定性与性能)
- **守**:Q3 Q7 — 大历史滚动性能、连接混沌测试(发送中杀连接)、畸形帧 fuzz
- **守的事故**:性能劣化、韧性、协议健壮性(bad magic 正是这类)
- **现状**:未建,后置

## 4. 双端场景库(L4 中枢,IM 测试的核心竞争力)

普通 App 单端自测即可;**IM 必须验证"两个端之间的通信结果"**。这是用户最痛 bug(丢消息/乱序/多端不同步)的唯一自动化防线,也是"可用性验收"的客观标准。

基于已有 `dual_test_helper.dart`,建成以下**可回归场景脚本库**(每条一个自动化用例):

| 场景 | 验证 | 守 |
|---|---|---|
| A 连发 100 条 → B 全收 + 顺序一致 + 无重复 | 投递正确性 | Q1 |
| B 离线时 A 发 50 条 → B 上线 → 补齐 50 条且不重 | 离线同步 | Q1 Q4 |
| A 在会话读消息 → B 端该会话未读归零 | 多端一致性 | Q4 |
| A 发 → 弱网/断连中途 → 重连后消息最终一致 | 连接韧性 | Q3 |
| A 换新设备 → 恢复密钥 → 打开历史密文 | E2EE 换机 | Q5 |
| A 发图/文件 → B 端 presign 授权后正常渲染 | 附件链路 | Q6 |
| 群里 A 发 → 群成员 B/C 全收 + 未读各自正确 | 群投递 | Q1 Q4 |

**这套脚本一旦建成,就是回答"软件到底可不可用"的客观依据**——比人工真机点点可靠、可回归、可纳入发版闸。

## 5. 质量门分级(什么拦合并 / 什么定时跑 / 什么发版前跑)

架构不只是"测什么",还有"何时强制"。**后端可容器化 → 契约层进硬门**:

| 门 | 覆盖层 | 时机 | 强度 |
|---|---|---|---|
| **合并硬门** | L0 + L1 + L2 + **L3(真后端)** + analyze/lint | 每次 PR | 🔴 红了禁止合并 |
| **每日回归** | L4 双端场景库 | nightly | 🟠 红了报警,不阻塞开发 |
| **发版闸** | L4 全量 + L5 性能 | release 前 | 🔴 红了禁止发版 |
| **周期体检** | L5 混沌 / fuzz | 每周 | 🟢 趋势观察 |

铁律:
- **L4 真机测试绝不进合并硬门**(慢、需设备、天然 flaky,会拖垮日常)——现在 `integration_test.yml` 想做但做死的教训。真机的正确位置是 nightly + 发版闸。
- **覆盖率不设全量硬线**(存量债会爆),只对**新增代码 patch 覆盖率**设 ≥70%,`fail_ci_if_error`。
- **Sonar 要么加 `qualitygate.wait` 做真门,要么明确降级为"仅报告"**,消除装饰门错觉。

## 7. 安全退役流程(可逆 · 分阶段 · 零硬删)

> 删代码有风险。所有清理遵循"可恢复优先"。

**三条铁律**
1. 全程在专用分支(`chore/test-cleanup`),`main` 不动 → `git checkout main` 即回原状。
2. 永不 `rm` 硬删;一律 `git rm`,留在 git 历史,可 `git checkout <sha> -- <file>` 恢复。
3. 删除类改动单文件、单独 commit,便于精确回滚。

**隔离 → 验证 → 删除(三步不跳步)**
```
步骤1 隔离  候选文件加 @Skip('待删除评估'),不删文件 → 跑一遍看有无依赖崩
步骤2 观察  确认被 skip 后没有"测试点覆盖"随之消失(对照它测的逻辑别处是否也测)
步骤3 删除  git rm 单独 commit → PR → review → 合并
```
分工:我负责准备/标记/`git rm` 到分支;**"跑测试验证绿"由 CI 或你触发**(遵你要求,我不运行测试)。

**退役对象分级**
- 🟢 可直接 git rm(已核实 0 活引用):`integration_test/` 下 `app_simple_test` `login_test` `simple_demo_test` `smoke_login_suite` `send_batch_c2c_test` `chat_test`
- 🟡 需先隔离验证:`ack_manager_enhanced_test` 内 2 个自证用例(删用例不删文件)、`conversation_state_mock_test` / `message_action_conversation_update_mock_test`(mock 测 mock)
- 🔴 需你决策:70-85 个 page 稻草人(部分应"升级为真测试"而非删)、`integration_test.yml` 修复 or 废弃、moment 三处重叠合并

## 9. 质量度量(判断"质量在变好",而非"测试通过")

- **缺陷逃逸率**:线上 bug 中"本该被某层拦住却漏了"的比例 → 反推补哪层
- **契约漂移拦截数**:L0/L3 拦下的前后端不匹配次数(应 >0,否则=没测真契约)
- **双端场景通过率**:L4 核心场景绿灯率 = "可用性"的直接度量
- **flaky 率**:同提交重跑不一致率,须 <1%(IM 时序测试天然易 flaky,不达标则测试不可信)
- **新增代码 patch 覆盖率**:≥70%(不追全量,避免存量债爆炸)
